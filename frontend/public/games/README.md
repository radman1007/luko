# بازی‌های آموزشی لوکو

بازی‌ها فایل‌های HTML مستقل (JS/CSS درون‌خطی) هستند که داخل iframe (با sandbox) در صفحه‌ی
اجرای بازی بارگذاری می‌شوند. برای اینکه از طریق URL سرو شوند، حتماً باید داخل `public/` باشند.

## افزودنِ بازی = فقط یک فایل با نامِ درست
هیچ کدی دستی عوض نمی‌شود. فایل را با نامِ درست در همین پوشه (`public/games/`)
بگذار؛ سرور جایگاهش را از روی نام حساب می‌کند و در مسیرِ همان کلاس می‌نشاند.

```
C1-Kr-F1-S2-G2.html        (یا فشرده: C1KrF1S2g2.html)
│  │  │  │  └─ G  شماره‌ی بازی در همان کتاب (از ۱)
│  │  │  └──── S  سیزن/هفته داخلِ همان فصل (از ۱)
│  │  └─────── F  فصل/ماهِ آموزشی (از ۱؛ F1 = مهر)
│  └────────── K  کتاب — فقط داخلی؛ هرگز به بچه نشان داده نمی‌شود
└───────────── C  کلاس (۱ تا ۶)
```

| کد | کتاب |
|---|---|
| `Kr` | ریاضی |
| `Ko` | علوم |
| `Kq` | قرآن |
| `Kn` | نگارش |
| `Kh` | هنر |
| `Kf` | فارسی |

کتابِ تازه = یک سطر در `BOOKS`ِ [backend/apps/games/naming.py](../../../backend/apps/games/naming.py).

خط‌تیره اختیاری است: `C1KrF1S2g2.html` و `C1-Kr-F1-S2-G2.html` یکی‌اند و
حروفِ بزرگ/کوچک فرقی نمی‌کنند.

### ترتیب
کلاس ← فصل ← هفته ← شماره‌ی بازی، **عددی** (G2 پیش از G10). شماره‌ی بازی در
هر کتاب جدا می‌رود، پس در یک هفته هم `Kr-g1` داریم هم `Kn-g1`؛ این‌ها پشتِ‌سرِ
هم و درهم روی مسیر می‌نشینند (اول همه‌ی g1ها، بعد g2ها) تا بچه یک‌نواخت یک
درس را پشتِ‌سرِ هم بازی نکند. دو فایل با یک (کلاس، کتاب، فصل، هفته، شماره)
تکراری‌اند. هر هفته دست‌کم یک بازی از هر کتابِ آن کلاس داشته باشد (گزارش اگر
نداشت هشدار می‌دهد). هر (فصل، هفته) روی نقشه یک هفته است و هفته‌ها پشتِ‌سرهم
باز می‌شوند؛ پوشه مهم نیست، فقط نام.

### بازی چطور «تمام شد» را خبر می‌دهد
اپ تا خبرِ پایان نرسد سکه نمی‌دهد و مرحله‌ی بعد را باز نمی‌کند. بهترین راه
یک خط در خودِ بازی است: `LUKO.finish()` (یا `LUKO.levelComplete()` برای
بازیِ چندمرحله‌ای).

بازی‌های استودیو این خط را ندارند. برای هر کدام جای دقیقِ بُرد در
[backend/apps/games/finish_points.py](../../../backend/apps/games/finish_points.py)
ثبت شده و `import_games` همان‌جا `lukoWin()` / `lukoCount()` / `lukoLevels()` را
می‌گذارد. پایان = پایانِ طبیعیِ بازی، یا اگر بازی خیلی بلند است (۲۰ تا ۵۰
مرحله) چند مرحله‌ی اولش — حدودِ ۳ تا ۶ دقیقه. باخت و خریدِ پوسته هرگز پایان نیستند.
**بازیِ تازه تا در این فهرست نیاید** فقط با
[`assets/luko-bridge.js`](assets/luko-bridge.js) تمام می‌شود که صفحه‌ی بُرد را
از روی شناسه‌اش حدس می‌زند؛ همین حدس بود که بعضی بازی‌ها را هرگز تمام نمی‌کرد و
بعضی را با باخت «تمام» می‌کرد. تستِ `apps/games/test_finish_points.py` بازیِ
بی‌نقطه‌ی پایان را می‌گیرد. باگ‌های خودِ بازی (مثلِ چاقوی نامرئیِ آزمایشگاهِ
میوه‌ها) در [game_fixes.py](../../../backend/apps/games/game_fixes.py) رفع می‌شوند.
اگر یک فایل با چند نام در چند جایگاه آمده باشد (نجاتِ قبیله، پیام‌های آسمانی)،
پیشرفتِ خودِ بازی بینِ آن‌ها مشترک است؛ `_in_slot` فقط مرحله‌هایی را می‌شمارد که
بچه در **همان** جایگاه برده، تا پایانِ یکی دیگری را خودبه‌خود تمام نکند.

### بعد از گذاشتنِ فایل
```bash
cd backend && python manage.py sync_games --check   # پیش‌نمایش؛ چیزی ذخیره نمی‌شود
```
گزارش مسیرِ هر کلاس، فایل‌های «نیاز به بررسی» با دلیلِ دقیق، و هشدارها را نشان
می‌دهد. روی سرور همین کار با دکمه‌ی «همگام‌سازی با فایل‌ها» در صفحه‌ی بازی‌های پنلِ
ادمین (یا `sync_games` بدونِ `--check`) انجام می‌شود.

- **نامِ غلط** (بخشِ جاافتاده، ترتیبِ دیگر، رقمِ فارسی، ` copy`، …) → «نامعتبر»؛
  هیچ‌وقت حدسی جا نمی‌گیرد. گزارش دلیل و در صورتِ امکان نامِ درست را می‌گوید.
- **دو فایل در یک جایگاه** → اگر یکی از قبل آن‌جا بوده می‌ماند و تازه‌وارد
  «تکراری» می‌شود؛ بازیِ سالمِ قبلی هیچ‌وقت به‌خاطرِ فایلِ تازه از مسیر بیرون نمی‌افتد.
- **جا باز کردن بینِ دو بازی**: بازی‌های بعدی را یکی جلو ببر (G3 → G4، …) و
  بازیِ تازه را بگذار. پیشرفتِ بچه‌ها با خودِ بازی‌ها جابه‌جا می‌شود، چون هویتِ
  هر بازی از محتوایش شناخته می‌شود نه از نامش. تغییرِ نام و ویرایشِ محتوا را در
  یک نوبت با هم نکن؛ وگرنه بازیِ تازه حساب می‌شود.
- **عنوان** از `<title>`ِ فایل می‌آید (بدونِ «LOKO …»، ایموجی و «بازیِ»)؛ بعد از
  آن از پنلِ ادمین عوض می‌شود و همگام‌سازی دیگر به آن دست نمی‌زند. اگر عنوان
  اسمِ درس را داشته باشد («مزرعه‌ی ریاضی») گزارش هشدار می‌دهد.
- پاداش‌ها (سکه/شبنم/کود/ستاره) و «فعال» هم در پنلِ ادمین‌اند.

منطق: [naming.py](../../../backend/apps/games/naming.py) (قالب و اعتبارسنجی) و
[registry.py](../../../backend/apps/games/registry.py) (پیدا کردن، تطبیق، جایگذاری).
صفحه‌ی بچه مسیر را از `GET /api/v1/games/path?grade=N` می‌گیرد که فقط عنوان،
ترتیب، هفته و پاداش دارد — هیچ نشانی از کتاب یا درس.

### ساختارِ پوشه
```
public/games/
  C1-Kr-F1-S1-G1.html …      ← خودِ بازی‌ها
  assets/                    ← دارایی‌های مشترک (بازی نیستند)
    luko-sdk.js  icons/  musics/  fonts/
  _reference/                ← پوشه‌ی `_…` بازی حساب نمی‌شود
```
بازی‌ها به دارایی‌ها با **مسیرِ مطلق** ارجاع می‌دهند: `/games/assets/icons/coin.png`.

## چرخهٔ عمر — بخوانید قبل از ساختِ بازیِ تازه

از نسخهٔ ۲، SDK یک ماشینِ حالتِ مشترک دارد که **پایانِ مرحله** را از
**پایانِ بازی** جدا می‌کند. مرجعِ کامل:
[`docs/game-architecture.md`](../../../docs/game-architecture.md).
نمونهٔ اجراشدنی روی dev server: `/games/_reference/base-game.html`.

سه خط برای هر بازیِ چندمرحله‌ای:

```js
LUKO.init({ gameType: 'sorting', totalLevels: MAX_LEVEL });  // اولِ اسکریپت
LUKO.startLevel(n, { title: cfg.title });                    // شروعِ هر مرحله
LUKO.levelComplete({ score });                               // به‌جای finish()
```

> **`finish()` یعنی «کلِ بازی تمام شد»، نه «این مرحله تمام شد».**
> گذاشتنش داخلِ `levelComplete` باعث می‌شد بازیِ چندمرحله‌ای بعدِ مرحلهٔ
> اول تمام‌شده حساب شود. حالا اگر بازی `totalLevels` را اعلام کرده باشد،
> SDK این صدازدن را به `levelComplete` تنزل می‌دهد و `finish_deferred` ثبت
> می‌کند — ولی درستش این است که خودِ بازی `levelComplete` صدا بزند.

بازی‌ای که `init()` را صدا نزند دقیقاً مثلِ نسخهٔ ۱ کار می‌کند.

## اتصال پایانِ بازی
اگر بازی خودش پایان را تشخیص می‌دهد، به والد پیام می‌دهد تا مرحله کامل و جایزه ثبت شود:
```js
window.parent.postMessage({ type: 'luko-game-complete' }, window.location.origin);
```
`BookGame` فقط پیام‌های هم‌ریشه را می‌پذیرد و جایزه را **یک بار** می‌دهد.
بازی‌هایی که این پیام را نمی‌فرستند، با دکمه‌ی «این مرحله رو تموم کردم» ثبت می‌شوند.

## قرارداد داده‌ی بازی (تله‌متری)
هدف: فرستادنِ رفتارِ ریزِ بچه به سرور و ساختِ گزارشِ والدین. مرجعِ پیاده‌سازی:
`_reference/base-game.html`.

بازی سه نوع پیام می‌فرستد (همه با `origin` خودمان):

| پیام | کِی | بار |
|---|---|---|
| `luko-game-event` | هر تعامل | `{ game, sessionId, event }` |
| `luko-game-complete` | پایانِ موفق (یک بار) | `{ game, sessionId, summary }` |
| `luko-game-progress` | بستنِ صفحه بدون اتمام (`pagehide`) | `{ game, sessionId, summary }` |

`event.type`های استاندارد: `game_start`، `station_start`، `select`، `swap`، `answer`
(با `correct/given/expected/ms/attempt/hintUsed/tier`)، `hint`، `station_end`، `idle`،
`away`، `setting`، `game_end`.

`summary` شاملِ: `accuracy`، `avgAnswerMs`/`medianAnswerMs`، `errors`، `hints`،
`idlePeriods`، `durationMs`، `device` و آرایه‌ی دورها (هر دور: نوعِ تمرین،
`tier` سختیِ تطبیقی، زمان، خطا، ستاره، و سنجه‌ی مخصوصِ همان بازی مثل
`moves` در برابر `optimalMoves`).

بازی‌هایی که چند مبحث را پوشش می‌دهند (مثل
`grade-6/game_6aval_riyazi.html`) روی هر `answer` یک
`topic` هم می‌گذارند و در `summary.topics` تسلطِ درس‌به‌درس را می‌دهند:
`{ fraction: { label, asked, correct, accuracy, avgMs, hints }, … }` — این دقیقاً
ورودیِ بخشِ «تسلط در درس‌ها» در پنل والدین است.

**وصل است:** [`features/games/telemetry.ts`](../../src/features/games/telemetry.ts) این پیام‌ها را
بافر می‌کند و دسته‌ای به `POST /api/v1/games/events` می‌فرستد (هر ۲۵ رویداد یا هر ۵ ثانیه،
و یک‌بار هم موقعِ بستنِ صفحه با `fetch keepalive`). پایانِ موفق علاوه بر آن
`POST /api/v1/games/{slug}/complete` را صدا می‌زند تا سکه را سرور بدهد.
گزارشِ پنل والدین دقیقاً از رویِ همین رویدادها ساخته می‌شود؛ پس بازی‌ای که
`answer` نفرستد، در «نقطه‌ی قوت و ضعف» دیده نمی‌شود.
برای دیدنِ زنده‌ی داده‌ها بازی را با `?debug=1` باز کنید؛ `window.LUKO_GAME.summary()` هم
در کنسول در دسترس است.

## آینده (React)
بازی‌های React بعداً به‌صورت route داخلی یا کامپوننت اضافه می‌شوند؛ فیلد `file` می‌تواند به
یک مسیر داخلی اشاره کند و در `BookGame` منطق تشخیص نوع بازی اضافه شود.
